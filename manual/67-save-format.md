# Формат сохранений

> Задача Ф1 этапа 7 ([план §9](plan/51-phase1-plan.md#9-этап-7-прогон-и-сверка)). Контракт —
> [`include/core_save/save.h`](../include/core_save/save.h); реализована задачей O1 (31.08.2026).
> Вопрос числился открытым в [решениях ядра](59-core-decisions.md) — этим документом закрыт.
> Номер формата — [`VERSION_SAVE`](../VERSION_SAVE), правила подъёма — [Версии §3](setup/57-versioning.md#3-когда-поднимать-version_save).

---

## 1. Решение в одну строку

**Сохранение — это `WorldState`, записанный поле за полем в двоичном виде, с ключами
таблиц определений впереди; при загрузке индексы перепривязываются по ключам, а
несовпадение номера формата — отказ, не миграция.**

---

## 2. Что сохраняется и что нет

| Сохраняется | Не сохраняется | Почему |
|---|---|---|
| `WorldState` целиком: календарь, погода, эпоха, seed, ГПСЧ, председатель, план, ПЖ, пять таблиц сущностей, ведомость, **книга распоряжений** | **Конфигурация подсистем** | Она не состояние: читается из таблиц при создании симуляции ([модель состояния §1](52-state-model.md#1-главное-решение-состояние--данные-системы--логика)) |
| **Книга распоряжений** `orders` — таблица как все | **Ящик шага** `step_events` | Распоряжение, которое ждёт, — состояние: его показывают и его можно отозвать ([граница §2](70-boundary.md#2-команды--это-книга-распоряжений)). Ящик описывает один шаг и опустошается движком в начале следующего — сохранять нечего |
| **Сложенная пачка** `staged` — то, что сессия приняла и движок ещё не применил | — | Единственное, что не `WorldState`: партия сохраняется на паузе, после раздачи нарядов, и потерять их значило бы наказать за непредвидимое. Пишет её тот, кто сохраняет, из `ISession::StagedBatch()` ([Стройка §7](71-construction.md#7-сохранение-один-подъём-version_save-за-три-изменения)) |
| `next_id_value` каждой таблицы | `row_by_id` | Индекс перестраивается при загрузке и потому не может разойтись с данными ([`state_table.h`](../include/core_common/state_table.h)) |
| **Ключи** пяти таблиц определений в порядке, в котором стояли их `DefId` | Сами таблицы баланса | Балансовая правка между сохранением и загрузкой — законна и ожидаема: игра продолжается на новых числах. Ключи нужны только чтобы понять, **те ли это строки** |

Вход сохранения — `ISimulation::CompletedState()` между шагами; выход загрузки — обратно
через `ISimulation::ResetWorld`. Сохраниться посреди шага нельзя по устройству API.

---

## 3. Ключи, а не индексы — главное решение

`DefId` — это номер строки балансовой таблицы, а `ResourceAmounts` — вектор, у которого
**сам индекс и есть `ResourceId`**: кладовая каждой семьи, склад каждого юнита, план.
Переставили строки в `resources.csv` между запусками — вектор, записанный по индексам,
переложит зерно в графу навоза, и ни одна проверка этого не заметит.

Поэтому:

| Правило | |
|---|---|
| **Впереди полезной нагрузки — словари** | Для ресурсов, культур, типов юнитов, видов скота и **должностей** (задача А7): число строк и их ключи в порядке `DefId` на момент записи |
| **Поле `DefId` пишется индексом, читается через словарь** | Загрузчик находит ключ в живой таблице (`FindRowByKey`) и подставляет новый индекс. `kInvalidDefIdValue` проходит как есть |
| **Плотный вектор переставляется** | Если хоть один ключ сменил индекс, вектор собирается заново размером с живую таблицу, каждое количество — под новым индексом своего ключа |
| **Тождественная перепривязка бесплатна** | Все ключи на своих местах — векторы копируются **как есть, вместе с длиной**. На тех же таблицах `Load(Save(w)) == w` почленно, включая длины векторов; это и проверяет unit-тест |
| **Пустой вектор остаётся пустым** | В обоих режимах: класть нечего, а пустая кладовая — это и есть «пока ничего не держит». Раздуть её до длины таблицы значило бы записать другое значение, а не то же самое |
| **Ключ из сохранения отсутствует в живой таблице** | Отказ **только если сохранение им пользуется**: поле `DefId` на него ссылается или под ним ненулевое количество. Нулевой столбец удалённого ключа выбрасывается молча — удаление неиспользуемого ресурса не должно убивать партию |
| **Ключ живой таблицы отсутствует в сохранении** | Просто нули. Добавить строку — ожидаемая дешёвая правка |

Правило «сохранения хранят ключи» записано в [таблицах баланса §3](61-balance-tables.md#3-схема-таблицы);
здесь оно исполняется.

## 4. Побитовость

| Правило | Зачем |
|---|---|
| **`float` пишется битами** (`std::bit_cast` → `u32`), никогда текстом | Потерять младший бит сытости — то же, что гонка: продолженная партия разойдётся с непрерывной |
| **`RngState` — два точных 64-битных слова** | Иначе следующий бросок другой |
| **Целые — little-endian побайтно, сдвигами** | Не `memcpy` структуры: паддинг и ABI двух компиляторов в формат не входят |
| Перечисления — их целым | |
| Строки — только ключи: `u16` длина + UTF-8 | |

## 5. Раскладка формата

```
   заголовок, 52 байта
     magic "KLHZSAVE"  8      format_version u32     header_size u16 (52)
     core major/minor/patch  u16 × 3  — справочно, не проверяются
     world_seed u64     tick u64     payload_size u64     payload_hash u64 (FNV-1a 64)

   полезная нагрузка — секции в жёстком порядке, каждая с префиксом длины u64
     словари: resources, crops, unit_types, livestock, professions
     calendar, weather, epoch, world_seed, rng, chairman, plan, vitals
     residents, families, fields, units, herds, orders  ← StateTable-секции
     ledger
     staged   ← сложенная пачка: u32 число строк, строки OrderRow, u32 число отмен, id
```

| Кодирование | |
|---|---|
| `StateTable` | `next_id_value` u32, число строк u32, идентификаторы u32, затем строки |
| **Строка** | Поля одно за другим **в порядке объявления в заголовке** |
| `ResourceAmounts` | u16 число, затем граммы i64 |
| `std::array<float, N>` | N float, без счётчика |
| `EntityId` | u32 как есть — **никогда не перепривязывается** |

Номер формата в заголовке — текущий [`VERSION_SAVE`](../VERSION_SAVE); раскладка выше
описывает его, и читается ровно он. **Секция `orders` добавлена задачей O1 второй фазы**
вместе с книгой распоряжений — отсюда `VERSION_SAVE` 3. **Задача А8 меняет раскладку одним
полем, `8 → 9`** (человек, 4 сентября 2026): `UnitRow::paused` — 0/1, остановлен ли юнит
([Наряды §6](76-work-orders.md#6-провод-и-версия-сохранения)). **Строка осталась 48 + `stock` —
байт лёг в паддинг**, см. §7: третий случай подряд. **Задача А4 меняет раскладку дважды, `7 → 8`** (человек, 3 сентября 2026): восьмой вид работы
удлинил колонку человеко-дней ведомости (`work_days_by_kind`), и у ведомости появился
`spoiled` — что сгнило за год, отдельной колонкой от `no_room`
([Логистика §5](75-logistics.md#5-порча-доля-от-лежащего-и-она-везде)). **Само перечисление
`WorkKind` формат не ломает** — виды дописываются в конец, — а вот массив, размеченный по
их числу, ломает. **Задача А7 меняет раскладку трижды и добавляет пятый словарь, `6 → 7`**
(человек, 3 сентября 2026): `ResidentRow::post` (строка 156 → 164),
`OrderRow::profession` (**строка осталась 48 — поле легло в паддинг**, см. §7),
`ChairmanState::horses_stabled` (12 → 16), словарь `professions`
([Должности §7](74-posts.md#7-сохранение-version_save-6--7)). **Задача А5 меняет раскладку одним полем,
`5 → 6`** (человек, 3 сентября 2026): износ постройки в строке юнита, `UnitRow::wear`
([Износ и ремонт §5](73-wear-and-repair.md#5-сохранение)). **Задача А3 меняет раскладку трижды
одним подъёмом, `4 → 5`** (человек, 3 сентября 2026): буфер полевой бригады в строке поля —
`reaped_grams` и `reaped_resource`, — и колонка ведомости `no_room`
([Склады и алармы §5](72-storage-and-alarms.md#5-сохранение-один-подъём-за-два-поля)).
**Задача А2 меняет раскладку трижды
одним подъёмом, `3 → 4`:** блок площадки в строке юнита (`UnitRow::construction`), цель наряда
на стройке (`WorkAssignment::unit`) и секция `staged`. Подъём — за человеком, при сдаче
реализации.

Префикс длины у секции нужен не для пропуска — пропускать нечего, читатель знает ровно
одну раскладку, — а чтобы **ошибка называла секцию**, а обрезанный файл ловился до
чтения первого поля.

`world_seed` и `tick` продублированы в заголовке ради `PeekSaveInfo`: меню перечисляет
сохранения — год, месяц, чья сборка — не разбирая тела. Календарь — чистая функция тика.

## 6. Отказы

**Загрузка — целиком или никак:** при любом отказе выходной `WorldState` не тронут, причина
уходит в `error` и в лог.

| Отказ | |
|---|---|
| Не та `magic` или короче заголовка | |
| **`format_version ≠ kSaveFormatVersion`** — и выше, и ниже | Ошибка называет оба числа. **Миграций в первой фазе нет:** игры не существует, ничьи партии не пострадают, а миграция, написанная до первого игрока, обслуживала бы никого |
| `payload_size` или `payload_hash` не сошлись | Обрезан или побит |
| Секция короче или длиннее, чем прочитано | Названа по имени |
| Ключ словаря отсутствует в живой таблице **и используется** | Назван по имени |
| Нарушен инвариант `StateTable`: дубль id, id ≥ `next_id_value`, выдан id 0 | |

**Игровые инварианты загрузчик не проверяет** — существует ли супруг, не больше ли самцов,
чем взрослых. Это дело симуляции; сохранению здесь верят так же, как верили буферу, из
которого оно записано.

**Но две проверки всё-таки его** — они не про игру, а про память:

| Проверка | Почему загрузчика |
|---|---|
| **Диапазон каждого `enum` в один байт** | Часть из них ниже по течению — **индексы массивов**: `WorkKind` в таблицу ставок, `Epoch` в конфигурацию эпохи. Битый байт читал бы за границей внутри фазы, далеко отсюда, и ничто не указывало бы на файл |
| **Потолок `next_id_value`** (2²⁴) | Массив обратного индекса выделяется по нему: счётчик в четыре миллиарда из повреждённого файла попросил бы шестнадцать гигабайт до чтения первой строки |

Календарные кэши (`day`, `date`, `weekday`, `season`) при загрузке **пересчитываются из
тика**, а не проверяются: это дешевле и строже — рассогласованная дата в фазу не попадёт.
Из календаря авторитетен только `day_zero_weekday`, и его диапазон проверяется.

## 7. Растяжка на `sizeof`

Единственный отказ, который формат **не может** поймать сам: поле добавили в строку, а в
писатель — нет. Оно молча потеряется и вернётся умолчанием.

**И есть случай, которого она не ловит: поле, легшее в существующий паддинг.** `sizeof`
тогда не меняется, а поток — меняется. Так `FieldRow` получил `LandKind` задачей О2б:
строка осталась 40 байт, а на каждое поле в потоке прибавился байт. Растяжка молчит,
и заметить это обязан человек ([Версии §3](setup/57-versioning.md#3-когда-поднимать-version_save)).

**Задача А7 повторила это на `OrderRow`** — `profession` лёг в дыру рядом с `work`, строка
осталась 48 байт — и показала, где промах дороже всего: **у журнала длина записи
фиксированная и посчитана вручную** (`core_boundary/journal_codec.cpp`, `kOrderBytes`).
Растяжка молчала, писатель уехал на два байта вперёд читателя, и поймал это не сторож, а
круговой тест журнала. **Правило: тронул список полей строки — пересчитай все длины «на
провод», а не только `sizeof`.**

**Задача А8 повторила это в третий раз** — `UnitRow::paused` лёг в паддинг после `level`, и
`sizeof` снова не двинулся. Три случая из трёх последних расширений строки: **это не редкая
неудача, а обычный исход.** Байт в строку почти всегда попадает в дыру, потому что дыры
там и есть — между полями разной ширины. Читать растяжку как «формат не менялся» нельзя
ни одного раза.

Поэтому реализация обязана держать `static_assert(sizeof(RowT) == <размер, под который
написан писатель>)` на каждый тип строки. Новое поле меняет размер — сборка падает, пока не
обновлены писатель, читатель и сам `assert`, а человек не поднял `VERSION_SAVE`. На x86-64
оба компилятора дают этим простым агрегатам один размер; если какая-то цель однажды
разойдётся, `assert` скажет об этом на этапе компиляции — а это всё ещё правильный момент.

## 7а. Длины перечислений выводятся, а не пишутся

**Каждое сериализуемое перечисление несёт последним элементом свой счётчик `k…Count`.** Оба
кодека берут верхнюю границу из него: `kMax… = k…Count - 1`.

**Счётчик — не значение.** Он не пишется в сохранение и не читается оттуда: дописанное перед ним
значение автоматически сдвигает и его, и границу. **Отстать он не может по построению.**

### Что было до этого и почему так нельзя

**Границы писались рукой — «последний элемент», — а над перечислением стояла инструкция:
«дописал вид — подними `kMaxOrderKind` в двух файлах».** Два дома у одной длины.

**И одна из копий отстала на две задачи.** А2 дописала два вида распоряжений, копия в
`journal_codec.cpp` осталась на `kDemolishUnit`, и **журнал с `kStartBuild` был бы отвергнут при
чтении.** Нашёл это проход по дизайну, а не что-либо работающее.

> **Правило, у которого механизм только в комментарии, — не механизм, а намерение. Намерение не
> проваливает проверку, потому что в ней не участвует** (boss, 4 сентября 2026).

### Две растяжки, и обе на этапе компиляции

| Что ловится | Чем |
|---|---|
| **Значение дописано ПОСЛЕ счётчика** | `switch` без `default` над этим перечислением: новый элемент — ошибка сборки. Это проверено — сигнальное значение растяжку не ослабило, оно лишь добавило один разбираемый случай |
| **Граница задана самим счётчиком, а не счётчиком минус один** | `static_assert` рядом с самими границами: она обязана быть **строго ниже** счётчика, иначе сигнальное значение прошло бы с провода |

**Ради потребителя, а не ради ядра.** Со счётчиком в публичном заголовке слой графики и хост
получают `static_assert` на длину своего зеркала: **короткое зеркало становится ошибкой сборки
вместо ошибки, ждущей своего случая.** У слоя было восемь причин отказа против наших девяти, и
сверить их было нечем.

### И поэтому счётчик есть не только у сериализуемых

**Первый заказ был сужен по признаку «сериализуемые» — те, у кого кодек проверяет диапазон.
Причиной же были зеркала**, а эти два множества совпадают не полностью.

**Разошлись они ровно в опасном месте:** `AlarmKind` и `EventKind` — те самые две таблицы, которые
**уже один раз молча разошлись** с зеркалом слоя, на шесть значений и на четыре. Сериализуемыми они
не были и остались без сторожа: **единственные зеркала со слабой защитой оказались те, что уже
подводили.**

> **Ограничение по признаку, который не был причиной, выглядит как аккуратность и работает как
> дыра** (boss, 4 сентября 2026). Прежде чем сузить правило, надо назвать вслух его причину и
> проверить, что признак сужения — она и есть.

Счётчики есть у `AlarmKind`, `EventKind` и `Whereabouts`. **Верхних границ у них в кодеках нет и не
нужно** — они не ездят в сохранении; счётчик у них существует ровно для зеркала потребителя.

## 8. Модуль

**`core_save`** — инфраструктурный ярус, лист графа: зависит от `core_common` (состояние)
и `core_tables` (живые ключи для перепривязки), не знает ни одной подсистемы, и от него не
зависит никто, кроме исполняемых и — позже — стороны UE. Не `core_world`: сериализация —
отдельный предмет, а не часть генезиса. Строка в [модулях §2](54-modules.md#2-модули-поимённо).

Два слоя API: **байты** (`EncodeWorld` / `DecodeWorld` / `PeekSaveInfo` — это и есть
формат; тесты гоняют круг через них) и **файлы** (`SaveWorldToFile` / `LoadWorldFromFile` /
`PeekSaveFile` — обёртки; движок волен владеть вводом-выводом сам).
