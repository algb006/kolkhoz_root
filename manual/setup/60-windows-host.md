# Windows-хост: настройка и сборка под MSVC

> Раскладка проекта и сборка в виртуалке — [Раскладка проекта](55-project-layout.md).
> Скрипты: [`scripts/win-setup.ps1`](../../scripts/win-setup.ps1) — настройка хоста,
> [`scripts/build-core.bat`](../../scripts/build-core.bat) — сборка на хосте,
> [`scripts/win-build.sh`](../../scripts/win-build.sh) — перенос и запуск с виртуалки.

---

## 1. Зачем нужен второй компьютер

```
   ВИРТУАЛКА (AlmaLinux 10)              ХОСТ (Windows 11 Pro)
   Clang, CMake, Ninja, ccache           MSVC из Build Tools
   основная разработка ядра        ──▶   сборка для линковки в UE
   прогоны симуляции                     игра и редактор UE
```

**Хост нужен только тогда, когда меняется библиотека, отдаваемая в UE.** Ядро обязано
собираться обоими компиляторами: расхождение между Clang и MSVC ловится сразу, а не в
редакторе через неделю ([Архитектура §7г](../../../manual/technical/50-architecture.md#7г-pipeline-разработки)).

**Основной цикл при этом остаётся в виртуалке** — там быстрее и там весь инструментарий.

## 2. Что ставится на хост и зачем

| Что | Зачем именно оно |
|---|---|
| **OpenSSH Server** | Штатный компонент Windows 11. Единственный вход на хост с виртуалки |
| **MSYS2** | Даёт `rsync` и POSIX-оболочку. **Без неё перенос не работает** — см. §5 |
| **Visual Studio Build Tools**, набор C++ | MSVC, Windows SDK, CMake и Ninja. Студия целиком не нужна |

Установлены **Build Tools 2026** (`C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools`,
MSVC 19.51). Номер года в пути меняется от выпуска к выпуску, поэтому
[`build-core.bat`](../../scripts/build-core.bat) ищет установку через `vswhere`, а не по пути;
CMake и Ninja берутся из самих Build Tools — в `PATH` их нет.

### Каталоги на хосте

**Общая папка игры — `C:\MyGames\Kolkhoz`**, по папке на часть проекта. Ядру принадлежит
`core-msvc`: исходники переносятся туда целиком, сборка кладётся в `build-msvc` внутри неё.

| Путь | В путях MSYS | Чьё |
|---|---|---|
| `C:\MyGames\Kolkhoz` | `/c/MyGames/Kolkhoz` | Общий корень игры |
| `C:\MyGames\Kolkhoz\core-msvc` | `/c/MyGames/Kolkhoz/core-msvc` | Ядро: `make win` |

**Доступ даёт учётная запись, а не каталог.** Вход по ключу открывает всё дерево хоста, не
только папку ядра, — отдельно открывать что-то под UE или под общий корень не нужно, и второй
ключ заводить тоже. Обе сессии агентов работают под одним пользователем виртуалки и делят
`~/.ssh/id_ed25519_win` и псевдоним `win`.

**Косая черта в путях имеет значение.** Оболочка на хосте — bash из MSYS2 (§5), поэтому в
командах пишется `/c/MyGames/...`, а не `C:\MyGames\...`; вид с двоеточием понимают только
`.bat` и сам Windows.

## 3. Как применить

Скрипт настройки лежит в репозитории ядра, а перенести его на хост до того, как заработает
SSH, нечем — поэтому проще всего отдать его по HTTP. **На виртуалке:**

```bash
make win-setup                                  # напечатает команды и публичный ключ
python3 -m http.server 8000 --directory scripts
```

**На хосте, в PowerShell от администратора:**

```powershell
irm http://192.168.1.6:8000/win-setup.ps1 -OutFile $env:TEMP\win-setup.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File $env:TEMP\win-setup.ps1 `
    -PublicKey "ssh-ed25519 AAAA... core-vm@alex-linux"
```

Ключ `-ExecutionPolicy Bypass` нужен потому, что политика по умолчанию не даёт запускать
никакие `.ps1` вообще. Она не меняется насовсем: ключ действует на один запуск.
Публичный ключ виртуалки печатает `make win-setup` — вставляется он целиком, одной строкой.

Скрипт **идемпотентный**: каждый шаг сначала смотрит, что уже сделано. Запускать повторно
после любой правки безопасно.

Когда вход по ключу проверен — закрыть вход по паролю:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File $env:TEMP\win-setup.ps1 `
    -LockPasswordAuth -SkipInstall
```

**Порядок здесь важен.** Выключить пароль до того, как заработал ключ, — значит остаться
без входа вообще.

## 4. Что скрипт выставляет

| Настройка | Значение | Почему так |
|---|---|---|
| Служба `sshd` | автозапуск, запущена | Иначе после перезагрузки хоста сборка молча недоступна |
| `DefaultShell` | `C:\msys64\usr\bin\bash.exe` | §5 |
| `DefaultShellCommandOption` | `-lc` | Логин-оболочка читает `/etc/profile`, без него `/usr/bin` не в `PATH` и `rsync` не находится |
| `DefaultShellEscapeArguments` | `0` | Экранирование аргументов ломает командную строку `rsync --server` |
| `PubkeyAuthentication` | `yes` | |
| Ключ | `C:\ProgramData\ssh\administrators_authorized_keys` | §5 |
| Профиль сети | `Private` | В профиле `Public` входящее закрыто целиком |
| Правило брандмауэра | порт 22 **только с адреса виртуалки** | Открывать 22 всему миру незачем |
| Каталог | `C:\MyGames\Kolkhoz\core-msvc` | |

Файл `sshd_config` правится на месте, копия сохраняется рядом как `sshd_config.bak`.

## 5. Три подвоха, на которых всё встаёт

**Первый: ключ администратора лежит не там, где ожидается.** Если учётная запись состоит в
группе администраторов, sshd **игнорирует** `C:\Users\<имя>\.ssh\authorized_keys` и читает
общий файл `C:\ProgramData\ssh\administrators_authorized_keys` — и только если права на него
не дают доступа никому, кроме `SYSTEM` и группы администраторов. Лишняя запись в правах — и
ключ отвергается молча, без внятного сообщения.

**Второй: `cmd.exe` не годится как оболочка для sshd.** `rsync` запускает на дальней стороне
`rsync --server ...` и ждёт разбора аргументов по правилам POSIX. Через `cmd.exe` командная
строка искажается, и перенос падает с `protocol version mismatch`, к версиям отношения не
имеющим. Поэтому оболочкой по умолчанию делается bash из MSYS2 — заодно понимающий пути вида
`/c/MyGames/...`.

**Третий: обратная сторона того же решения.** Раз оболочка на хосте — bash, `.bat` вызывается
через `cmd`, а MSYS переписывает всё, что начинается со слэша, в путь Windows. Ключ `/c`
превратился бы в `C:/`, поэтому в [`win-build.sh`](../../scripts/win-build.sh) стоит **`cmd //c`**:
двойной слэш — принятый в MSYS способ сказать «это не путь».

## 6. Проверка с виртуалки

```bash
ssh win 'uname -a; rsync --version | head -1'   # оболочка и rsync на хосте
make sync                                        # только перенос, без сборки
make win                                         # перенос и сборка
```

| Команда | Что делает |
|---|---|
| `make sync` | Перенос `rsync --checksum`, без сборки |
| `make win` | Перенос и сборка Debug |
| `make win-release` | То же, Release |
| `make win-clean` | Снести каталог сборки Debug на хосте и собрать заново |
| `make win-setup` | Напомнить порядок первичной настройки и показать публичный ключ |

Другой хост или каталог — `make win WIN_HOST=... WIN_DIR=...`.

**Собранная библиотека забирается обратно** в `artifacts/<конфигурация>/core.lib`; каталог
в `.gitignore`.

## 6а. Публикация: что именно забирает слой графики

**Каталог сборки — рабочее место, а не витрина.** Там недособранное, там обломки прерванной
сборки, там файлы, которых никто не обещал. Поэтому у ядра есть **публикация** — отдельное
понятие и отдельный каталог, у которого **ровно один писатель: `build-core.bat`**.

```
   C:\MyGames\Kolkhoz\core-msvc\
     build-msvc-Debug\      мастерская            ← сюда не смотреть
     build-msvc-Release\    мастерская
     publish\
       Debug\               include\  lib\core.lib  VERSION
       Release\             include\  lib\core.lib  VERSION   ← это берёт ue
```

| Правило | Почему |
|---|---|
| **Каталог сборки у каждой конфигурации свой** | Раньше обе писали в один `build-msvc`, и в `lib\core.lib` лежал тот, кого собрали последним. **Снаружи различить было нечем** |
| **Слою графики нужен Release** | Редактор UE поставляется двоичным, с `/MD` и `_ITERATOR_DEBUG_LEVEL=0`. Debug-сборка ядра для него — `LNK2038`, и перевести редактор на отладочный CRT **невозможно в принципе**, а не неудобно |
| **Публикация переписывается целиком** | Каталог сносится и пишется заново. Файл, который там лежит, положила **эта** сборка, а не какая-то прошлая |
| **`VERSION` лежит рядом с библиотекой** | Не в дереве исходников, а в том же каталоге, что и `.lib`. Только так потребитель может упасть громко на устаревшем артефакте вместо того, чтобы тихо с ним слинковаться |
| **В чужое дерево ядро не пишет** | `ue` забирает сам. Чужой проект — не наша файловая система |
| **`publish/` исключён из `rsync`** | Иначе `--delete` сносил бы опубликованное при каждом переносе: в дереве виртуалки такого каталога нет |

### Одна библиотека, а не две

**Публикуемая `core.lib` — это `core.lib` и `enkiTS.lib`, слитые `lib.exe` в один архив.**

Своя `core.lib` не линкуется в одиночку: у неё восемь неразрешённых символов `enki::` из
движка шага. Выкладывать два файла значило бы протащить **наш** выбор планировщика в чужой
скрипт сборки, а [`CLAUDE.md` §7](../../CLAUDE.md) говорит: у ядра **одна** выходная
библиотека. Заголовки enkiTS при этом не публикуются — ни один наш публичный заголовок его
не упоминает, планировщик целиком за границей.

**Проверено линковщиком, а не рассуждением:** пробный `.cpp`, собранный `/MD` против
опубликованного Release, линкуется с нулём; тот же файл против Debug даёт ровно те
`LNK2038` про `_ITERATOR_DEBUG_LEVEL` и `RuntimeLibrary`, на которых встал `ue`.

### Свежесть

**Обещанием «не забуду синхронизировать» это не чинится**, поэтому механизм двусторонний:

| Кто | Что делает |
|---|---|
| **Ядро** | Кладёт `VERSION` рядом с библиотекой. Сменился номер — **посылка в одну строку**: опубликовано столько-то |
| **`ue`** | Держит ожидаемый номер у себя под гитом и **роняет сборку**, если не совпало. Поднять ожидаемый — его отдельный коммит |

`win-build.sh` вдобавок сверяет номер, который вернулся с хоста, с номером в дереве. Разойтись
они в норме не могут — хост собирал ровно то, что только что перенесли; **если разошлись,
значит в каталог хоста писали мимо скрипта**, и это отказ, а не предупреждение.

### Дыра, которую нашёл слой: подъём версии публикацию не двигает

**Случилось 31 августа 2026 на `1.0.0`.** Номер поднят, отправлен, объявлен — а на хосте
осталась `0.8.1`, и слой упёрся в собственную проверку пина. **Проверка сработала как задумано;
дыра была в порядке действий, а не в механизме.**

**Причина в том, что команд две, и цикл сдачи гоняет не ту.** `/check_static_new` собирает
MSVC-сборку в **Debug** — этого хватает, чтобы поймать расхождение компиляторов, ради которого
шаг и заведён. А слой берёт **Release**, и его публикует отдельная команда `make win-release`,
которую цикл не вызывает и вызывать не должен: не всякая сдача обязана выкладываться наружу.

**Поэтому напоминание встроено туда, где расхождение рождается** — в `scripts/bump_version.sh`.
Подняв номер, скрипт говорит, что публикация на хосте осталась на прежнем, и называет команду.
Он не публикует сам: выкладка наружу — решение человека, а не побочный эффект правки файла.

| Правило | |
|---|---|
| **Поднял `VERSION` — выложи Release**, если слой на нём стоит | Иначе следующая его сборка встанет |
| **Цикл сдачи Release не публикует** | Сдача модуля и выпуск наружу — разные события |
| **Слой пин не обходит** | Он вернул его на прежний номер и работал дальше. Так и правильно |

## 7. Почему перенос по содержимому, а не по времени

`rsync` вызывается с ключом **`--checksum`**: отметки времени между виртуалкой и хостом
разъезжаются, и сравнение по ним то пропускает изменённый файл, то гоняет неизменённый.
Ключ `--delete` убирает с хоста то, чего в исходниках больше нет, — иначе удалённый модуль
продолжает собираться там ещё долго.

**Привычного `-a` здесь нет, и это не оплошность.** Он включает `-p -o -g`, а права POSIX на
NTFS через MSYS2 не ставятся: файл доезжает, а следом падает
`failed to set permissions ... Permission denied`. Берётся `-rltz` — то, что хосту
действительно нужно.

Из переноса исключены каталоги сборки, `.git/`, `claude/`, `artifacts/` и **`publish/`**:
сборка хоста своя, остальное на хосте не нужно. **Исключение `publish/` — не косметика:**
этого каталога в дереве виртуалки нет, и без исключения `--delete` сносил бы опубликованное
при каждом переносе, прямо перед тем как собрать его заново.

## 8. Если не работает

| Симптом | Причина |
|---|---|
| Хост не пингуется, порт 22 закрыт, но ARP отвечает | Брандмауэр. Профиль сети `Public` либо правило не создано |
| `Permission denied (publickey)` | Ключ не в `administrators_authorized_keys` либо права на файл шире, чем `SYSTEM` + администраторы |
| `protocol version mismatch` при переносе | Оболочкой sshd остался `cmd.exe` или `powershell.exe` |
| `rsync: command not found` | `DefaultShellCommandOption` не `-lc`: без `/etc/profile` в `PATH` нет `/usr/bin` |
| `cmd` жалуется на `C:/c` | Потерялся двойной слэш в `cmd //c` |
| `vswhere not found` | Build Tools не установлены или встали без набора C++ |
| `failed to set permissions ... Permission denied` | В `rsync` вернулся ключ `-a` (§7) |
| **То же самое, но с ключами из §7 и только на новых файлах** | **Разовая гонка на стороне хоста:** только что созданный файл ещё держит индексатор или антивирус. **Лечится повтором `make win`** — второй заход всегда проходит. Наблюдалось трижды, на переносах с большим числом новых файлов |
| `'scriptsbuild-core.bat' is not recognized` | Оболочка хоста съела обратный слэш: имя `.bat` должно быть в одинарных кавычках |
| `scp: Connection closed` | С bash в роли оболочки sshd подсистема sftp не работает, а `scp -O` не находит на хосте `scp.exe`. **`scp` к этому хосту не использовать** — файлы ходят через `ssh cat`, как в `win-build.sh` |
| Собралось, а библиотека старая | Инкрементальная сборка. `make win-clean` |
| `LNK2038: _ITERATOR_DEBUG_LEVEL` у потребителя | Взят `publish\Debug` вместо `publish\Release`. Редактору UE нужен Release, и это не настройка, а свойство его поставки (§6а) |
| `unresolved external symbol` про `enki::` | Взята библиотека из каталога сборки, а не из `publish\`. Слияние с `enkiTS.lib` делает шаг публикации (§6а) |
| Скрипт отказался: «на хосте одна версия, в дереве другая» | В каталог хоста писали мимо `win-build.sh`. Разбираться, кто, а не пересобирать поверх |
