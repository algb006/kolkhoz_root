## 1. Каталоги

| Каталог | Что внутри | Кто трогает |
|---|---|---|
| [`include/`](../../include/) | **Общие заголовки всех модулей.** То, что модуль показывает наружу | Все модули |
| [`subprojects/`](../../subprojects/) | **Модули ядра.** Папка на модуль, каждый — объектная цель CMake | Ядро |
| [`src/`](../../src/) | **`main.cpp` игры.** Вторая фаза, сейчас пусто | Игра |
| [`tests/`](../../tests/) | **Консольные приложения:** тесты и прогоны симуляции | Проверка |
| [`depends/`](../../depends/) | Сторонние библиотеки **в исходниках** | Сборка |
| [`libs/`](../../libs/) | Сторонние библиотеки **готовыми `.a` и `.lib`** | Сборка |
| `tables/` | **Таблицы баланса, CSV.** Правятся без пересборки ([Таблицы баланса](../61-balance-tables.md)) | Балансировщик |
| [`scripts/`](../../scripts/) | Сборка на Windows-хосте, git-хуки | Инфраструктура |
| `manual/` | Эта документация | Люди |
| `build/` | Результат сборки, в git не попадает | Никто |

**Глубже трёх уровней не заходим** ([Архитектура §7д](../../../manual/technical/50-architecture.md#7д-требования-к-коду)).

### Где лежит заголовок

**Развилка одна: видит его кто-то снаружи модуля или нет.**

| Заголовок | Куда | Почему |
|---|---|---|
| **Интерфейс подсистемы, общие типы** | **`include/<модуль>/`** | Его включают другие модули |
| **Внутренняя реализация модуля** | Рядом со своим `.cpp` в `subprojects/<модуль>/` | Никто снаружи о нём не знает |

**Папка в `include/` называется точно как модуль.** Не для красоты: по пути
`include/core_time/calendar.h` механически восстанавливается модуль `core_time`, а по нему —
метка `@threading`, от которой зависит состав проверок статанализа
([Статанализ и тесты §4](56-static-analysis-and-tests.md)). Включение выглядит как
`#include "core_time/calendar.h"` — по строке видно, чей это интерфейс.

**Каждый `#include` в заголовке тянет за собой дерево — это время сборки.**
Поэтому в `include/` попадает только то, без чего снаружи не обойтись
(`CLAUDE.md` §6).

---

### `depends/` и `libs/` — разные вещи

| | `depends/` | `libs/` |
|---|---|---|
| Что лежит | **Исходники** | **Собранные архивы** |
| Как подключается | `add_subdirectory` | `find_library`, импортированная цель |
| Пересобирается | Вместе с нами | Никогда |
| Наши предупреждения | **Не применяются** | Неприменимо |

**Чужой код не собирается с нашими `-Werror`.** Он не наш, править его мы не будем.

**Что ожидается в `depends/` на первой фазе:** enkiTS (планировщик задач),
`moodycamel::ReaderWriterQueue` (очередь на границе с презентацией), Dear ImGui
(интерфейс прогона, этап 7).

## 2. Как из модулей получается библиотека

```
   subprojects/core_common/     ──┐
   subprojects/core_time/       ──┤  объектные цели CMake
   subprojects/core_residents/  ──┤
   subprojects/core_land/       ──┘
                                  │
                                  ▼
                            build/lib/libcore.a    одна библиотека
```

**Одна выходная библиотека.** Внутри — модули как объектные цели
(`CLAUDE.md` §7). Так граница между модулями проверяется системой сборки:
не объявил зависимость — не собралось.

### Как объявить модуль

Папка `subprojects/<имя>/` с `CMakeLists.txt`. Внутри:

```cmake
kolkhoz_add_module(core_time
    time_service.cpp
    calendar.cpp)

target_link_libraries(core_time PRIVATE core_common)
```

**`kolkhoz_add_module` делает три вещи:** создаёт объектную цель, вешает на неё
общие настройки и заголовки, записывает её в список для сборки `core`.

**Папки подхватываются автоматически** в алфавитном порядке — порядок ссылок
детерминирован. Отдельно прописывать модуль в списке не нужно, **но зависимости
между модулями объявляются вручную и всегда.**

| Правило | |
|---|---|
| **`core_common` — база** | Типы, идентификаторы, математика. От неё зависят все |
| **Модули не зависят друг от друга напрямую** | Только через интерфейсы в `include/` |
| **Потянулись друг к другу — граница неверна** | Сказать об этом, а не добавить зависимость |

**Пока модулей нет, библиотека `core` не создаётся** — сборка проходит и ничего
не выдаёт. Это нормальное состояние до этапа 1.

---

### Как объявить тестовое приложение

**Тестов два вида, и лежат они в разных местах.**

| | Где | Чем объявляется | Обязателен |
|---|---|---|---|
| **Unit-тест модуля** | `tests/unit/<модуль>/` | `kolkhoz_add_unit_test(<модуль> main.cpp)` | **Да, на каждый модуль** |
| Прогон и всё прочее | `tests/run/<имя>/` | `kolkhoz_add_test_app(<имя> main.cpp)` | По необходимости |

```cmake
# tests/unit/core_time/CMakeLists.txt
kolkhoz_add_unit_test(core_time main.cpp)

# tests/run/thirty_years/CMakeLists.txt
kolkhoz_add_test_app(thirty_years main.cpp)
```

Помощник соберёт исполняемый файл, прилинкует `core` и зарегистрирует его в CTest.
Unit-тесты получают метку `unit`, поэтому:

```
  make unit          только обязательные тесты модулей
  make test          весь набор, включая длинные прогоны
  make check-tests   на каждый ли модуль есть тест
```

**Модуль без unit-теста сдавать нельзя** — правило и порядок сдачи в
[Статанализ и тесты](56-static-analysis-and-tests.md).

Прогоны на тридцать лет, числа которых сверяются с
[`../balance/49-simulations.md`](../balance/49-simulations.md), живут в `tests/run/`.

> **Открытый вопрос:** библиотека модульных тестов в документах дизайна не
> выбрана. Пока обходимся обычными исполняемыми файлами с кодом возврата —
> этого хватает, и выбор откладывается до реальной нужды.

## 3. Команды

**Собирает CMake плюс Ninja. `Makefile` — только обёртка**, чтобы не помнить
ключи. Полный список — `make help`, пояснения — `README.txt`.

| Команда | Что делает |
|---|---|
| `make build` | Debug, с настройкой при необходимости |
| `make release` | Release |
| **`make rebuild`** | **С нуля. Первое, что делать при странном поведении** |
| `make test` | `ctest` по всем приложениям из `tests/` |
| `make asan` | Сборка с `address` и `undefined` |
| `make format`, `make tidy` | Форматирование и статический анализ |
| `make docs` | Выжимка Doxygen в `build/doc` |
| `make sync`, `make win` | Перенос на Windows-хост и сборка под MSVC |
| `make info` | Что установлено, какие настройки действуют |

### Ключи настройки

| Ключ | По умолчанию | |
|---|---|---|
| `KOLKHOZ_BUILD_TESTS` | `ON` | Собирать `tests/` |
| `KOLKHOZ_BUILD_GAME` | `OFF` | Собирать `src/` — вторая фаза |
| `KOLKHOZ_WERROR` | `ON` | Предупреждения как ошибки |
| `KOLKHOZ_SANITIZERS` | пусто | Например `address;undefined` |

---

### Про инкрементальную сборку

**Изменился двоичный формат структуры или перечисления, пересобралось не всё —
получается битая сборка без единой ошибки компиляции.**

| Мера | |
|---|---|
| **Правил заголовок с данными — `make rebuild`** | Это секунды |
| **Странное поведение — `make rebuild` первым делом** | До всякой отладки |
| **`rsync --checksum`, не по времени** | Отметки времени между машинами разъезжаются |

**Ядро собирается за секунды при любом раскладе** — сборка с нуля ничего не стоит.

## 4. Две машины

```
   ВИРТУАЛКА (AlmaLinux 10)              ХОСТ (Windows)
   Clang, CMake, Ninja, ccache           MSVC из Build Tools
   основная разработка ядра        ──▶   сборка для линковки в UE
   прогоны симуляции                     игра и редактор UE
```

**Основной цикл — в виртуалке.** Хост нужен только тогда, когда меняется
библиотека, отдаваемая в UE: ядро обязано собираться обоими компиляторами,
расхождения ловятся сразу ([Архитектура §7г](../../../manual/technical/50-architecture.md#7г-pipeline-разработки)).

```bash
make win        # rsync --checksum, затем build-core.bat на хосте
```

**Первичная настройка хоста — [Windows-хост](60-windows-host.md).** Там же
скрипт, который её выполняет, и разбор подвохов: ключ администратора лежит не
там, где ожидается, а `cmd.exe` не годится оболочкой для `sshd`.

| Команда | Что делает |
|---|---|
| `make sync` | Только перенос, без сборки |
| `make win` | Перенос и сборка Debug |
| `make win-release`, `make win-clean` | Release; пересборка с нуля на хосте |
| `make win-setup` | Порядок первичной настройки и публичный ключ виртуалки |

## 5. Настройка инструментов

| Файл | Что задаёт |
|---|---|
| [`.clang-format`](../../.clang-format) | Google C++ Style, ширина строки 100 |
| [`.clang-tidy`](../../.clang-tidy) | Набор проверок и **правила именования** из `CLAUDE.md` §4 |
| [`.gitattributes`](../../.gitattributes) | **Окончания строк LF**, `.bat` — CRLF, двоичные файлы |
| [`Doxyfile`](../../Doxyfile) | Выжимка по интерфейсам, тег `@threading` виден в выводе |
| `scripts/git-hooks/pre-commit` | Форматирование при коммите |

**Правила именования проверяются `clang-tidy`, а не глазами на ревью:** типы и
функции `PascalCase`, переменные `snake_case`, поля класса `snake_case_`,
константы `kPascalCase`, абстрактные интерфейсы `IPascalCase`, глобальные
переменные `g_snake_case`.

### Приставки `I` и `g_`

**Обе решают одну задачу: сказать по имени то, чего не видно по фрагменту кода.**

| | Что означает | Проверка |
|---|---|---|
| **`IUnitRegistry`** | Класс **абстрактный** — это контракт подсистемы, а не реализация | `AbstractClassPrefix` |
| **`g_frame_counter`** | Переменная живёт **вне всякой области видимости** | `GlobalVariablePrefix` |

**`I` вешается ровно на абстрактные классы** — те, у кого есть чисто виртуальный
метод. Реализация приставки не получает: `Granary`, а не `IGranary`.

**`g_` — только у изменяемых глобальных.** Глобальные константы остаются
`kPascalCase`: они не меняются, прятаться им негде.

> **`g_` не разрешает глобальное состояние.** Изменяемая глобальная переменная
> ломает детерминизм — жёсткое требование (`CLAUDE.md` §10). `clang-tidy`
> продолжает ругаться на каждую такую переменную
> (`cppcoreguidelines-avoid-non-const-global-variables`), и это сделано
> нарочно: приставка называет вещь своим именем, а не выдаёт разрешение.
> Проверка предупреждает, но сборку не валит — решение остаётся за автором.

### Уточнение про `const` у локальных переменных

`CLAUDE.md` §4 требует **`const` везде, где возможно** — и он же требует
**`kPascalCase` у констант**. Буквально вместе эти два правила означали бы `k`
почти у каждой локальной переменной, что бессмысленно. Разделено так:

| Что | Как называется | Пример |
|---|---|---|
| **Константа в пространстве имён, у класса, статическая** | `kPascalCase` | `kMaxResidents` |
| **Локальная `constexpr`** — это именованная константа | `kPascalCase` | `constexpr int kWorkDays = 41;` |
| **Локальная `const`** — это обычная переменная, которую не меняют | `snake_case` | `const int hunger_level = ...` |

**Смысл `const` у локальной переменной — «не меняется дальше», а не «это
константа настройки».** Именованные константы, ради которых введено правило про
магические числа, объявляются `constexpr` и получают `k`.

### Что ещё требует `clang-tidy`

| Проверка | |
|---|---|
| **Include guard, а не `#pragma once`** | `portability-avoid-pragma-once`. `#pragma once` — не часть стандарта, а ядро собирается двумя компиляторами |
| **Никаких `printf` и прочих varargs** | `cppcoreguidelines-pro-type-vararg`. Есть `std::format` из C++20 |
| Именование макросов | `UPPER_CASE`. Защита включения (`RESIDENT_STATE_H_`) — исключение |

**Что намеренно выключено:** `modernize-use-nodiscard` — требует `[[nodiscard]]`
почти у каждого константного метода, а правила такого в проекте нет.
`cppcoreguidelines-special-member-functions` настроена так, что **одинокий
виртуальный деструктор у интерфейса нарушением не считается**: без этого каждый
интерфейс требовал бы пяти объявлений.

Форматирование включается один раз командой `make hooks` — она направляет git
на `scripts/git-hooks`. **Хук правит только файлы, попавшие в коммит**, и молча
пропускает работу, если `clang-format` не установлен: коммит он не блокирует.

## 6. Что установить

**AlmaLinux 10, репозитории EPEL и CRB** — оттуда Ninja и ccache.

```sh
sudo dnf install -y epel-release
sudo dnf config-manager --set-enabled crb
sudo dnf install -y clang clang-tools-extra lld cmake ninja-build \
                    ccache doxygen git rsync
```

То же печатает `make deps`. Что уже установлено — покажет `make info`.

| Инструмент | Зачем |
|---|---|
| **Clang** | Санитайзеры, `clang-tidy`, тот же LLVM, что в toolchain консолей |
| **CMake плюс Ninja** | Одинаково в виртуалке и на хосте, надёжнее Make с зависимостями |
| **ccache** | Кеш **по содержимому** — переживает `rsync` и смену отметок времени |
| **`clang-tools-extra`** | `clang-format` и `clang-tidy` |
| Doxygen | Выжимка по интерфейсам |

**`ccache` стоит ограничить:** `ccache --max-size=5G`.
