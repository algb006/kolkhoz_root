# Статанализ и тесты: что обязательно при сдаче

> Раскладка проекта и сборка — [Раскладка проекта](55-project-layout.md).
> Правила написания кода — [`../../CLAUDE.md`](../../CLAUDE.md) §10, §14.

**Этот документ — источник правды для правила.** Сам механизм живёт в файлах, которые в git
не попадают (`claude/`, `.claude/` — они под `.gitignore` и хранятся в архиве
`/claude_backup`). Правило должно пережить потерю механизма, поэтому записано здесь.

---

## 1. Два обязательства

| Что | Когда обязательно |
|---|---|
| **Unit-тест на модуль** | Модуль (связка `.h` + `.cpp`) не сдан, пока теста нет и он не прогнан |
| **Статанализ `/check_static_new`** | При сдаче модуля и **при сдаче фазы разработки кода игры** |

**Прочие тесты — по необходимости.** Прогоны симуляции, сверка с расчётами, проверки на стыке
подсистем заводятся тогда, когда есть что проверять, и живут в `tests/run/`.

---

## 2. Unit-тест на каждый модуль

```
   subprojects/core_time/     модуль
        │
        └── tests/unit/core_time/     ← обязательный тест, имя папки = имя модуля
                 приложение unit_core_time, метка CTest "unit"
```

| Правило | |
|---|---|
| **Имя папки теста = имя модуля** | Связь механическая, а не по договорённости |
| **Объявление** | `kolkhoz_add_unit_test(core_time main.cpp)` |
| **Метка CTest** | `unit` — `make unit` гоняет ровно обязательный набор |
| **Проверка полноты** | `make check-tests` |

`make check-tests` ловит обе стороны расхождения: модуль без теста и тест без модуля
(переименовали модуль — тест остался прикрывать пустоту).

```
  make unit          только обязательные тесты модулей
  make test          весь набор, включая прогоны из tests/run/
  make check-tests   на каждый ли модуль есть тест
```

**Библиотека модульных тестов не выбрана** — в документах дизайна решения нет. Пока
обходимся обычными исполняемыми файлами с кодом возврата: `0` — прошёл, иначе — упал. Этого
хватает, выбор откладывается до реальной нужды.

## 3. Статанализ: `/check_static_new`

Команда гоняет цикл **сборка → тесты → анализ → правки** по дельте от последней успешной
проверки, на четыре класса дефектов: **UB**, **Memory**, **RACE**, **DEADLOCK**.

| | |
|---|---|
| **Где живёт команда** | `.claude/commands/check_static_new.md` — **в git не попадает** |
| **Хелпер сборки** | `claude/tools/core_build.sh` — тоже не попадает |
| **Данные и отчёты** | `claude/analysis/` — тоже не попадают |
| **Откуда взято** | Посылка из родительского проекта, адаптирована под ядро |

**Цикл правит исходники и работает прямо на `main`** — у ядра один разработчик и одна
ветка, она же рабочая, защищать отдельной веткой нечего. Вместо неё дерево защищает
снимок, который цикл делает **до первой правки**: он единственный способ отделить правки
цикла от незакоммиченной работы человека. Отсюда же запрет на `git stash` и
`git checkout -- .` внутри цикла — именно они эту работу и снесли бы.

Отказ один: **detached HEAD**. Коммит сдачи ушёл бы туда, где на него ничто не ссылается.

Режим `--once` — один проход только для чтения, без сборки и правок.

### Что цикл проверяет и чего не делает

| Делает | Не делает |
|---|---|
| Анализ **по дельте**, а не всего дерева | Полный аудит кодовой базы |
| Чинит `crit` и внесённые самим циклом `high` | Не пишет код ради `med` и `low` |
| Копит остальное в `claude/analysis/OPEN_ITEMS.md` | Не переоткрывает разобранное заново |
| Правит комментарии **одним проходом в конце** | Не ревьюит прозу в каждой итерации |

**Потолок — восемь итераций, и он жёсткий.** Формулировка «гоняй, пока не станет чисто» его
не снимает: цикл ревьюит собственные свежие правки, поэтому пустой проход недостижим по
построению. Условие успеха — **правки цикла не внесли `crit` и `high`**, а не «находок нет».

## 4. Однопоточный модуль не проверяется на гонки

**Метка `@threading` в шапке заголовка решает, какие классы анализа запускать.** Она
существует ровно за этим: анализатор не ищет гонки там, где их не может быть
(`CLAUDE.md` §10).

| Метка модуля | Классы анализа |
|---|---|
| **`SINGLE_THREADED`** | **UB и MEM. RACE и DEADLOCK не запускаются** |
| `PARALLEL_READONLY` | все четыре |
| `PARALLEL_WRITE` | все четыре |
| **метки нет** | **все четыре**, плюс находка «метка отсутствует» |

**Два предохранителя, оба в сторону «лучше проверить лишнее»:**

1. **Метки нет — гоняем всё.** Метка обязательна; её отсутствие — само по себе находка.
   Иначе «забыл метку» стало бы способом обойти проверку.
2. **Метка говорит `SINGLE_THREADED`, а в коде есть `std::thread`, мьютекс, атомик или
   задача enkiTS** — это находка класса RACE серьёзности **критическая**, и модуль
   проверяется на гонки **всё равно**. Смена метки — событие, молча ей верить нельзя.

Есть и третий случай: **две разные метки внутри одного модуля**. Это дефект, а не выбор —
тоже все четыре класса и находка.

Классификация делается **скриптом, а не глазами**: `claude/tools/threading_scope.sh` строит
по списку файлов таблицу «файл → модуль → метка» и отдельный список тех файлов, которые
получают RACE и DEADLOCK. Метка модуля берётся только из его собственных каталогов —
`include/<модуль>/` и `subprojects/<модуль>/`, поэтому **папка в `include/` называется точно
как модуль** ([Раскладка проекта](55-project-layout.md)).

Находки про метку — единственные находки про документацию, которые цикл чинит **сразу**, а не
в общем doc-проходе: от метки зависит состав классов следующей итерации.

## 5. `tests/` вне механизма

**Статанализ каталог `tests/` не обслуживает.** Там анализ упрощённый и только по
необходимости — флагом `--with-tests`.

| Почему | |
|---|---|
| **Дефект в тесте виден как упавший тест** | Он не уезжает в поставку |
| **Тест — леса, а не конструкция** | Полный аудит лесов ради трёхстрочной правки бессмыслен |
| **Цикл ревьюит собственные правки** | Расширение области — прямой путь к несхождению |

Упрощённый проход отличается по всем осям: только **UB и MEM**, только по хункам, без
разбора комментариев, и находки **сдачу не блокируют** — уходят в `OPEN_ITEMS.md` с пометкой
`tests`.

**Когда включать `--with-tests`:** тест сам стал сложным (генератор данных, сверка с
эталонными числами), тест падает непонятно, прогон даёт разные числа от запуска к запуску.
В остальных случаях — не включать.

## 6. Порядок сдачи

### Сдача модуля

```
  1. make check-tests                    на модуль есть unit-тест
  2. make unit                           тест проходит
  3. /check_static_new                   цикл до успешного прохода
  4. коммит                              область схлопывается, следующий цикл дешевле
```

### Сдача фазы разработки кода игры

Всё то же, плюс требования `CLAUDE.md` §14:

| Проверка | Чем |
|---|---|
| **Собирается в виртуалке без предупреждений** | `make rebuild` — `-Werror` включён |
| **Собирается на хосте под MSVC** | `/check_static_new --flavour` или `make win` |
| **Весь набор тестов проходит** | `make test` |
| **Один поток = много потоков** | Сверка двух прогонов, когда появится планировщик |
| **Статанализ прошёл по всей дельте фазы** | `/check_static_new` |
| Форматирование, размеры файлов, `@brief`, `@threading`, `STUB` | `make format-check`, ревью |

**Маркер базы сдвигается только при успешной сдаче.** Прерванный или досрочно остановленный
прогон маркер не трогает: иначе дельта, которую никто не анализировал, будет похоронена.

## 7. Если механизм потерян

Файлы механизма не отслеживаются git — при потере восстанавливаются из архива
`/claude_backup`. Что должно быть на месте:

| Файл | Роль |
|---|---|
| `.claude/commands/check_static_new.md` | Сама команда: вся механика цикла |
| `claude/tools/core_build.sh` | Хелпер сборки: `preflight`, `build`, `test`, `syntax` |
| `claude/tools/threading_scope.sh` | Классификация файлов по метке `@threading` |
| `claude/analysis/` | Маркер базы, открытые пункты, отчёты, журналы |

**Что при этом остаётся в git и потерю переживает:** это правило, раскладка `tests/unit/`,
помощник `kolkhoz_add_unit_test`, `scripts/check_module_tests.sh` и цели `make unit` и
`make check-tests`. То есть обязательства сохраняются, восстанавливать нужно только
инструмент.
